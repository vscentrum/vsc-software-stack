## KU Leuven build setup

Central idea: one repository (`foz-software-stack`, hosted on KU Leuven gitea server) determines the entire state of our installed software^(1)^. The biggest difference with `vsc-apps-bot` is that we do not trigger an installation for a specific PR; instead, a pipeline runs whenever the main branch is updated that brings the state of the actually installed software in line with the repository definition.

### Main ingredients of the repository

- Three types of data files:
    - **stack files**: list of modules, very close to an easystack. Differences are that we allow some additional options regarding permissions^(2)^ and resources (e.g., request additional memory when installing CP2K)
    - **osarch files**: one for each combination of OS and architecture. Contains information about how to submit jobs to the corresponding nodes and a list of toolchain versions (2024a, 2025a, etc) to install.
    - **recipes**: collections of easyconfigs and easyblocks (official repos as submodules, custom versions just inside repo). In principle not limited to EasyBuild, but currently we only use EasyBuild.
- The `foz-install-stacks` script (Python) that generates jobscripts based on the data files of the repo and what is currently installed. Those jobscripts install the software that is currently missing.
- A Jenkins pipeline that can talk to our cluster using the Slurm REST API. It submits a "wrapper" job that executes `foz-install-stacks`, from which the actual install jobs are submitted.

![image](https://hackmd.io/_uploads/r1VzsmHSWg.png)

### Details

- We usually do test installations for PRs, which use a scratch directory for installations (instead of `/apps` in production)
    - Currently not possible to transfer test installation to production, installation simply runs again. The `bwrap` approach would be interesting.
- When new hardware is taken into production or the OS is updated, it suffices (in principle) to generate a new "osarch" file, indicating the desired toolchain versions. When running the pipeline, all software for the new hardware/OS is installed in one go (in practice, we try to split up the jobs somewhat, for instance first making sure all toolchains install correctly).
- ^(1)^ Updates in for instance the easyconfigs submodule can break the strict correspondence between the repository and the state of `/apps` (e.g., there is no automatic rebuild in case an easyconfig for an already installed module is updated)
- ^(2)^ We install software with our admin accounts, which cannot be made member of VSC groups. This causes some headaches when licensed software needs to be installed (we are looking into improving this).
